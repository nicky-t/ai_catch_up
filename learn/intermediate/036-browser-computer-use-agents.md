# 036 ブラウザ操作・コンピュータ操作エージェントの現在地

!!! abstract "この記事で説明できるようになること"
    - 「スクリーンショット主導型」と「DOM/アクセシビリティツリー主導型」という2つの操作エージェント方式の違い
    - なぜ座標ズレ・コスト膨張・プロンプトインジェクションが起きやすいのか
    - 業務でどちらの方式を選ぶべきかの判断基準

## 仕組み

画面やブラウザを操作するAIエージェントは、大きく2方式に分かれる。

**① スクリーンショット主導型**（Claude Computer Use、OpenAI Operator/CUAなど）
人間の目と手を模倣する方式。Anthropicの「Computer use tool」は次の4段階ループで動く（出典: Claude Platform Docs）。

1. モデルにスクリーンショットと操作指示を渡す
2. モデルが `left_click`・`type`・`scroll` などの操作（`tool_use`）を返す
3. 実際に環境で操作を実行し、結果（新しいスクリーンショット）を返す
4. タスク完了と判断するまで1〜3を繰り返す

座標はモデルに渡した画像のピクセル空間で返ってくるため、解像度を変えた場合はアプリ側でスケーリング計算が必須になる。小さい文字は `zoom` アクションで対象領域を拡大して読ませる。

**② DOM/アクセシビリティツリー主導型**（browser-use など多くのブラウザ自動化ツール）
画面を画像として見るのではなく、Webページの構造（DOM）やOSのアクセシビリティ情報から要素の位置・種類を直接取得して操作する方式。画像を都度モデルに渡す必要がないため、トークン消費が少なく高速な傾向がある。

## 比較・判断基準

| 観点 | スクリーンショット主導型 | DOM/アクセシビリティツリー主導型 |
|---|---|---|
| 得意な対象 | デスクトップアプリ・レガシーシステムなどAPIもDOMも取れない画面 | Webアプリ・ブラウザ操作全般 |
| コスト・速度 | 画像1枚あたり1,000〜1,800トークン程度が毎ターン蓄積し高コスト化しやすい | 構造情報のみのやり取りで軽量・高速 |
| 頑健性 | 見た目が変わらない限り比較的頑健。解像度変更時は座標スケーリングが必要 | UIの見た目変更には強いが、DOM構造の大幅な変更には弱い |
| 導入の手軽さ | 隔離されたVM・仮想ディスプレイの用意が前提 | ブラウザ拡張・ヘッドレスブラウザで比較的手軽 |

業務で選ぶ際は「対象がWebかデスクトップか」「操作対象のUIがどれだけ頻繁に変わるか」「1回あたりの許容コスト」を軸に判断するとよい。

## 落とし穴

1. **座標ズレ**：スクリーンショットの解像度と実画面の解像度がずれていると、クリック位置が意図と異なる場所になる。スケーリング係数の計算を省略するとよく起きる失敗。
2. **プロンプトインジェクション**：スクリーンショットや取得したページ内容に埋め込まれた指示文をエージェントが実行してしまうリスクがある。Anthropicは分類器でスクリーンショットをスキャンし、疑わしい指示は実行前にユーザーへの確認を挟む設計を採る。
3. **トークン・コストの膨張**：長いループで過去のスクリーンショットが蓄積すると、画像トークンだけで文脈窓を圧迫する。定期的に古い画像を破棄する、キャッシュを活用するなどの運用設計が必要。

## 実務への接続

- ログイン画面や社内システムなど、公式APIが提供されていない業務ツールの定型操作（データ入力・帳票ダウンロードなど）の自動化に使える
- 認証情報を直接エージェントに渡さず、人間が事前ログインした状態を引き継ぐ、または専用の隔離環境（VM・コンテナ）で実行するのが安全な運用の前提
- 今日の「現場ネタ」で紹介したbrowser-use/video-useのように、動画編集など「画面操作以外の反復作業」を任せる用途にも同じ設計思想（エージェントに繰り返し操作させ、結果を確認させる）が応用されている

## 講座で使うなら

- 30 秒説明: 「AIに画面を操作させる方法には、人間のように画面を"見て"クリックする方式と、Webページの内部構造を直接読み取る方式の2種類があります」
- たとえ話: 前者は「画面を写真で確認しながら操作する人」、後者は「設計図を見ながら操作するロボット」
- 演習案: 受講者の業務にある「画面操作だけの繰り返し作業」を1つ挙げてもらい、Webアプリかデスクトップアプリかで、どちらの方式が向くか議論させる
