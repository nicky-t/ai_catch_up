# 013 プロンプトの構造化：役割・制約・手順・出力形式・例の5要素

!!! abstract "この記事で説明できるようになること"
    - プロンプトを「役割・制約・手順・出力形式・例」の5要素に分解して設計する方法
    - Claude公式ドキュメントが推奨する「明確さ」「役割付与」「例示」「XMLタグでの構造化」の実践ポイント
    - 要素を詰め込みすぎたときに起きる落とし穴

## 仕組み

良いプロンプトは思いつきの一文ではなく、次の5つの要素を意識的に組み合わせて作られる。

1. **役割（role）**：システムプロンプトで「あなたは〜の専門家です」と一文設定するだけでも、口調や判断基準が変わる。Anthropic公式ドキュメントは、たった一文の役割設定でも違いが出るとしている
2. **制約（constraints）**：やってはいけないこと・守るべき条件（文字数、禁止表現、扱ってよい範囲など）
3. **手順（steps）**：順序や網羅性が結果を左右する作業は、番号付きリストや箇条書きで明示する
4. **出力形式（output format）**：JSON・表・見出し構成など、期待するアウトプットの形を先に示す
5. **例（examples）**：Few-shot（少数例示）。公式ドキュメントは3〜5個の例を含めるのが望ましいとし、例は`<example>`タグ（複数なら`<examples>`タグ）で囲んで指示文と区別させることを勧めている

さらに、指示・文脈・入力データなど性質の異なる内容が混在するプロンプトでは、`<instructions>`や`<context>`のようなXMLタグで種類ごとに囲むと、Claudeが誤読しにくくなるとされている。構造に階層がある場合（複数の文書を渡すときなど）は、タグを入れ子にすることも推奨されている。

## 比較・判断基準

| 要素 | 効果が大きい場面 | 省いてよい場面 |
|---|---|---|
| 役割 | トーン・専門性を揃えたい対話型タスク | 単発の機械的な変換タスク |
| 制約 | 出力の逸脱コストが高い業務利用 | 探索的な下書き作成 |
| 手順 | 順序・網羅性が結果を左右する作業 | 単純な要約・分類 |
| 出力形式 | 後続処理でパースする／人が読む形が決まっている | 自由記述で十分な相談ごと |
| 例 | 望む出力パターンが説明しにくい | 指示だけで一意に伝わるタスク |

Claude公式ドキュメントが挙げる判断の出発点は「黄金律」：そのプロンプトを、文脈をほとんど持たない同僚に見せて、迷わず実行できるかどうかを基準にする、という考え方である。

## 落とし穴

1. **役割づけだけで満足してしまう**：「あなたは優秀な〇〇です」と書いても、出力形式や手順が曖昧なままでは効果が限定的
2. **例が少なすぎる／似すぎている**：例が1つだけだと、Claudeがその例特有の細部までパターンとして学習してしまう。公式ドキュメントは、実際のユースケースに近く、かつ多様な例を複数用意することを勧めている
3. **XMLタグを付けずに要素を詰め込みすぎる**：指示・文脈・処理対象のデータを地の文で混在させると、どこまでが指示でどこからが処理対象かをモデルが誤認しやすくなる

## 実務への接続

社内向けのプロンプトテンプレートを作る際は、この5要素を空欄付きのフォーマットとして用意しておくと、非エンジニアの担当者でも「役割」「出力形式」だけ埋めれば一定品質のプロンプトを作れるようになる。研修でも「まず5要素のどれが欠けているか」をチェックリスト化すると、受講者のプロンプトを添削しやすい。

## 講座で使うなら

- 30 秒説明: 「良いプロンプトは思いつきの文章ではなく、役割・制約・手順・出力形式・例という5つの部品を組み合わせて作ります」
- たとえ話: 新人に仕事を頼むときの依頼メール——役職への言及（役割）、やってはいけないこと（制約）、作業順序（手順）、納品物の形式（出力形式）、過去の見本（例）が揃っているほど、相手は迷わず動ける
- 演習案: 受講者が普段使っている雑な1行プロンプトを1つ持ち寄らせ、5要素のどれが欠けているかを一緒にチェックして書き直させる
