# 043 ガードレール：入出力フィルタと業務ルールの実装

!!! abstract "この記事で説明できるようになること"
    - ガードレールが「入力」「対話・実行」「出力」のどの段階で効くものかを説明できる
    - 既存のモデレーションAPI・ガードレールフレームワークが何を検出でき、何を検出できないかを説明できる
    - 自社でガードレールを組むときに、モデルの安全設計と業務ルールをどう分けて考えるかを判断できる

## 仕組み

ガードレールは、AIの入出力を「AIまかせにしない」ための仕組みで、動く段階によって性質が異なる。

- **入力ガードレール**：ユーザーの入力を生成前に検査する。有害な指示・プロンプトインジェクション・業務外の質問を弾く
- **対話・実行ガードレール**：エージェントがツールを呼び出す際、許可された操作の範囲を超えていないかを実行時にチェックする（例：本番データベースへの書き込み禁止）
- **出力ガードレール**：モデルの生成結果を、ユーザーに返す前に検査する。有害コンテンツ・個人情報（PII）の漏えい・業務ルール違反を検出する

OpenAIの Moderation API は出力（および入力）を13カテゴリ（ハラスメント・ヘイト・違法行為・自傷・性的コンテンツ・暴力など）でスコアリングする無料のエンドポイントで、生成と同時に検査する「インラインモデレーション」と、生成なしでテキストだけを分類する「スタンドアロン分類」の2通りの使い方がある。結果は真偽値の`flagged`と各カテゴリ0〜1のスコアで返る（出典: OpenAI Moderation guide、2026-09-30取得）。

一方、NVIDIAのNeMo Guardrailsはより広い範囲をカバーするオープンソースのPythonライブラリで、入力・検索・対話・実行・出力という複数の段階にレールを差し込める。Colangという専用言語で「ボットが議論してよいトピック／いけないトピック」を対話フローとして定義でき、ジェイルブレイク検出・PIIのマスキング・カスタムアクションにも対応する（出典: NVIDIA NeMo Guardrails documentation、2026-09-30取得）。

両者に共通するのは、**「モデルの学習に頼らず、外側のプログラムでチェックする」**という発想である。モデル自身がいくら賢くなっても、業務ルール（「見積金額は必ず承認者を経由する」など）はモデルの知識ではなく組織の規則なので、外側のロジックとして実装する必要がある。

## 比較・判断基準

| 種類 | 何を防ぐか | 実装コスト | 向いている場面 |
|---|---|---|---|
| 既製のモデレーションAPI（OpenAI Moderationなど） | ヘイト・暴力・性的コンテンツなど汎用的な有害性 | 低い（API呼び出しのみ、無料） | 不特定多数向けチャットの最低限の安全対策 |
| ガードレールフレームワーク（NeMo Guardrailsなど） | トピック逸脱・ジェイルブレイク・PII漏えいなど、より業務寄りの逸脱 | 中〜高（設定・対話フロー定義が必要） | 社内向けアシスタント、業務範囲を限定したいエージェント |
| 自前の業務ルール（承認フロー・金額上限など） | 「規則として決まっている」制約全般 | 高い（要件定義から自作） | 既製ツールではカバーできない、自社固有のルール |

既製のモデレーションAPIは「一般的に問題のあるコンテンツ」は防げるが、「この会社ではこの金額を超えたら承認が要る」といった業務固有のルールまでは防げない。業務ルールは結局、自前で実装するか、ガードレールフレームワークの中にカスタムアクションとして書き込む必要がある。

## 落とし穴

1. **出力フィルタだけで満足してしまう**：有害な出力を止めても、危険な操作（ツール呼び出し）自体は止まっていない場合がある。エージェントがツールを使う構成では、実行段階のチェックも別に必要
2. **汎用モデレーションで業務ルール違反まで防げると誤解する**：ヘイトスピーチ検出と「見積書に不正な金額を書かせない」は全く別の問題。既製APIのカバー範囲を過信しない
3. **フィルタを厳しくしすぎて業務が止まる**：誤検知（false positive）が多いと、正当な業務利用まで弾かれる。検知の閾値は本番投入前に自社データで検証する

## 実務への接続

社内でAIエージェントを導入する際は、「モデルが賢くなれば安全になる」ではなく、「モデルの外側にどんなチェックを置くか」を先に設計する方が現実的である。最低限の順番としては、(1) 既製のモデレーションAPIで汎用的な有害性を弾く、(2) エージェントがツールを使うなら実行段階の権限チェックを入れる、(3) 自社固有の業務ルールはカスタムロジックとして別に実装する、という3段階で考えると抜け漏れが少ない。

## 講座で使うなら

- 30秒説明: 「AIの入力と出力を、AIとは別のプログラムでチェックする仕組みです。空港の手荷物検査のように、本人（モデル）を信用しきらずに毎回チェックします」
- たとえ話: 新人社員がどれだけ優秀でも、稟議の承認フローは省略しないのと同じで、AIにも「賢さとは別に守らせるルール」がある
- 演習案: 自社で使っているAIチャットに「言わせたくないこと」を1つ挙げてもらい、それが入力段階・出力段階・業務ルールのどこで止めるべきかを議論させる
