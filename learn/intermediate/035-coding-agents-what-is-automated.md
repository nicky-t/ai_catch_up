# 035 コーディングエージェント（Claude Code等）：何が自動化され、何が人に残るか

!!! abstract "この記事で説明できるようになること"
    - コーディングエージェントが「計画→実装→検証→コミット」のどこまでを自動化するかを説明できる
    - CLAUDE.md・Hooks・サブエージェントなど、自動化の範囲を人間側が設計・制御する仕組みを説明できる
    - 「エージェントに任せる」ことと「エージェントを止める仕組みを持つ」ことが別問題である理由を説明できる

## 仕組み

コーディングエージェントは、029で扱った「エージェントの基本形（ループ・ツール・状態・停止条件）」をソフトウェア開発というドメインに特化させたものといえる。Claude Codeの公式ドキュメントは、その自動化範囲を次のように説明している（[Claude Code Overview](https://code.claude.com/docs/en/overview)、取得日2026-09-22）。

- **コードベースの理解と横断編集**：リポジトリ全体を読み込み、複数ファイルにまたがる実装・バグ修正を行う
- **コマンド実行と検証**：テストの実行・失敗の修正・lintエラーの解消などを、ツール呼び出しを通じて自ら行う
- **Gitとの直接連携**：変更のステージング・コミットメッセージの作成・ブランチ作成・プルリクエスト作成までを担う
- **外部ツール接続（MCP）**：Google DriveやJira、Slackなど社内ツールと接続し、設計文書の参照やチケット更新まで一連の作業に組み込める
- **並列実行**：複数のサブエージェントに作業を分担させ、統括役（リードエージェント）が結果をまとめる仕組みも用意されている

一方で、自動化の「範囲」そのものは固定ではなく、人間側が設計するレイヤーが用意されている。`CLAUDE.md`（プロジェクトのコーディング規約・アーキテクチャ方針を常に読み込ませるファイル）、Hooks（編集後の自動フォーマットやコミット前のlintなど、特定のタイミングで任意のコマンドを挟む仕組み）、Skills（`/review-pr` のような再利用可能な定型ワークフロー）が、それに当たる。つまり「何を自動化するか」は既定の機能ではなく、CLAUDE.md・Hooks・Skillsという3つの設定レイヤーの組み合わせで、チームごとに調整するものとして設計されている。

## 比較・判断基準

| 観点 | 完全に自動化しやすい | 人に残しやすい |
|---|---|---|
| 定型作業 | テスト作成・lint修正・依存関係更新・リリースノート作成 | — |
| 実装 | 単一〜少数ファイルの機能追加・バグ修正 | アーキテクチャ変更・複数チームにまたがる設計判断 |
| 検証 | 自動テストの実行と失敗修正 | 「テストが本当に仕様を表しているか」の判断 |
| Git操作 | コミット・ブランチ作成・PR作成 | マージ判断・レビュー承認・本番デプロイの最終承認 |
| 外部ツール接続 | チケット更新・ドキュメント参照 | 誰にどこまでのアクセス権を与えるかの設計 |

判断基準はシンプルで、「結果を機械的に検証できるか」（テストが通る・lintが通る・ビルドが通る）と「後戻りのコストが低いか」（コミット単位で差分を見て取り消せるか）の2軸が高いほど自動化に向く。逆に、検証基準そのものが曖昧な設計判断や、本番環境への影響が大きい操作は、エージェントが提案し人間が承認する形に残しやすい。

## 落とし穴

1. **「動く」と「正しい」を混同する**：テストが通ってもテスト自体の設計が甘ければ、エージェントは「検証を通過した誤り」を量産できてしまう。自動化を広げるほど、テスト・lintという検証基準の質が全体の品質上限を決める。
2. **権限設計を後回しにする**：どのツール・外部サービスへのアクセスを許可するかを個別タスクごとに都度判断していると、承認疲れで「とりあえず許可」が常態化しやすい。プロジェクト開始時にCLAUDE.md・Hooksで権限方針を先に決めておく方が破綻しにくい。
3. **並列実行を検証なしで信頼する**：複数のサブエージェントに作業を分担させる場合、統括側が各成果物を突き合わせて矛盾がないか確認する工程を省くと、一見整った変更が実は互いに矛盾したまま統合されるリスクがある。

## 実務への接続

業務効率化の文脈では、「自動化できる部分を広げる」ことよりも「どこで人間の承認を挟むか」を先に設計する方が、導入後のトラブルを防ぎやすい。例えば、テスト・lintが整備された定型的な保守作業（依存更新、既知バグの修正）は早い段階で任せ、本番デプロイや複数チームに影響する設計変更は、エージェントに「提案」までを担わせ人間が最終承認する、という段階的な任せ方が現実的な出発点になる。

## 講座で使うなら

- 30 秒説明: 「コーディングエージェントは、コードを読む・書く・実行する・コミットするまでを一気通貫でこなせますが、"どこまで自動化するか"は使う側がCLAUDE.mdやHooksという設定で決められます」
- たとえ話: 新人に仕事を任せるとき、マニュアル（CLAUDE.md）を渡し、提出前チェック（Hooks）を挟み、最終承認だけは自分がする——それをソフトウェアの仕組みとして持たせたもの
- 演習案: 受講者の担当業務から「検証基準がはっきりしている定型作業」を1つ選ばせ、それをエージェントに任せる場合の承認ポイントを設計させる
