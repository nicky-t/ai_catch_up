# 026 長文コンテキスト vs RAG：どちらを選ぶかの判断基準

!!! abstract "この記事で説明できるようになること"
    - 「コンテキストウィンドウが大きいのでRAGは不要では」という誤解に、コスト・速度・精度の3面から反論できる
    - 長文コンテキストとRAGのどちらを選ぶかを、具体的なトリガー条件で判断できる

## 仕組み

学習記事005で扱った通り、コンテキストウィンドウは各社100万トークン級まで広がった。「全部読ませれば検索は要らないのでは」という発想は自然だが、実際には精度・速度・コストの3つで無視できない差が出る。

- **精度**：Wikipedia的な百科事典型の質問応答では長文コンテキストが有利という報告がある一方、対話的なクエリや一般的な質問では検索（RAG）が優位という逆転が確認されている（出典: arXiv "Long Context vs. RAG for LLMs"）。また「ニードル・イン・ヘイスタック」（大量の文章に1つだけ埋め込んだ事実を探すテスト）ではGemini 1.5 Proが99.7%の再現率を記録した一方、複数の事実を横断的に拾う必要がある現実的なタスクでは平均再現率が約60%まで下がるという実測もある（出典: tianpan.co）。
- **速度**：RAGパイプラインが1クエリあたり約1秒で完結するのに対し、16万トークン級の長文コンテキスト呼び出しは約20秒、89万トークン級では60秒を超えるとされ、30〜60倍遅い（同出典）。
- **コスト**：同出典の試算では、10万トークンを毎回読み込ませるコスト（GPT-4.1で1クエリ約0.20ドル）は、RAGクエリ1件（約0.00008ドル）のおよそ1,250倍に達する。

## 比較・判断基準

| 観点 | 長文コンテキストが有利 | RAGが有利 |
|---|---|---|
| タスクの性質 | 文書全体を横断した要約・推論 | 事実の正確な抽出・出典の明示 |
| コーパスの規模 | ウィンドウに収まる量 | ウィンドウを超える量（ハードリミット） |
| レイテンシ要件 | 多少待てるバッチ処理 | 対話的で数秒以内の応答が必要 |
| クエリ量 | 少量・低頻度 | 大量・高頻度（コスト差が支配的になる） |
| データの鮮度 | 静的な文書セット | 頻繁に更新される情報 |

tianpan.co の判断フレームワークでは、これらを「コーパスがウィンドウを超える」「レイテンシがSLOに違反する」「クエリ量がRAGとのコスト逆転点を超える」「データガバナンス上、外部送信を最小化したい」の4つの具体的なトリガーとして整理している。

## 落とし穴

1. **「ウィンドウが広い＝精度が高い」という思い込み**：広告される上限トークン数と、実際に複数の事実を取りこぼさず拾える実効再現率は別物
2. **少量データでもRAGを組んでしまう**：コーパスが小さくクエリ頻度も低いなら、素直に全文をコンテキストに入れる方が構築・運用コストが低い場合がある
3. **どちらか一方に決め打ちする**：実運用では「まずウィンドウに収まるか判定し、収まらなければ検索に回す」というルーター型の併用構成が現実的

## 実務への接続

社内文書検索（学習記事025）のように出典の明示や権限フィルタが必須な業務では、コストと再現率の面でRAGが依然として有利になりやすい。一方、少数の長い契約書や議事録をその場で要約・横断質問させたいだけなら、長文コンテキストへの直接投入の方が構築コストは低い。「まず母集団のサイズとクエリ頻度を見積もる」ことが最初の分岐点になる。

## 講座で使うなら

- 30 秒説明: 「AIの記憶容量（コンテキストウィンドウ）がいくら広がっても、検索（RAG）が要らなくなるわけではありません。速さとコストの差が大きいからです」
- たとえ話: 分厚い辞書をその場で毎回全部読み直す（長文コンテキスト）か、必要なページだけ付箋で探して開く（RAG）かの違い
- 演習案: 受講者に「自分の業務で扱う文書量」と「1日に質問する回数」を書き出してもらい、上の比較表のどちらに近いか判定させる
