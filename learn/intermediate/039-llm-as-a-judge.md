# 039 LLM-as-a-judge：AIの出力をAIで評価する設計と落とし穴

!!! abstract "この記事で説明できるようになること"
    - LLM-as-a-judge（LLMに出力を評価させる手法）の代表的な3パターンを説明できる
    - 人手評価との使い分けと、評価を自動化する際の設計原則を説明できる
    - position bias・self-preference biasなど、判定側LLMが陥りやすい落とし穴を説明できる

## 仕組み

「LLMに出力を評価させる」といっても、出す答えの形を絞るほど再現性が上がる。Anthropicの公式ドキュメントは代表例として3パターンを挙げている。

1. **Likert scale（尺度評価）**：トーンや共感性など主観的な側面を1〜5などの尺度で採点させる。「1: 全く共感的でない」〜「5: 完全に共感的」のように各段階の基準を明記するのがコツ
2. **binary classification（二値判定）**：個人情報（PHIなど）の露出検知のように、yes/noで機械的に切り分けられる観点を判定させる
3. **ordinal scale（順序尺度）**：複数ターンにわたる会話で「文脈をどれだけ活用できたか」のような、比較可能だが連続量ではない評価に使う

どのパターンでも、判定用プロンプトは「数値だけを出力させる」「基準を段階ごとに明文化する」など、出力形式を構造化して自動採点しやすくすることが前提になっている。

## 比較・判断基準

| | 人手評価 | LLM-as-a-judge |
|---|---|---|
| 速度・量 | 遅い・少数サンプルが限界 | 速い・大量のテストケースを回せる |
| コスト | 高い（評価者の人件費） | 低い（API呼び出し費用のみ） |
| 一貫性 | 評価者間でぶれる | プロンプトが同じなら再現しやすい |
| 深い妥当性 | 人間の暗黙知を反映できる | 判定側LLM自身の偏り・誤りをそのまま反映する |

Anthropicのドキュメントは「量を優先し、自動採点できる形に問いを構造化する」ことを設計原則として掲げている。実務では、量で回せるLLM判定を土台にしつつ、重要な意思決定が絡む出力だけ人手レビューを残す、という二段構えにするのが現実的な落としどころになる。

## 落とし穴

- **判定に生成モデルと同じモデルを使う**：Anthropicのドキュメントも「生成に使ったモデルとは別のモデルで評価するのが一般的なベストプラクティス」と明記している。同じモデルで採点すると自分の出力を甘く採点しやすい
- **position bias（提示順バイアス）**：2つの出力を並べて比較させる方式では、先に提示した方を高く評価しやすい傾向が知られている。順番を入れ替えて2回判定する、といった対策が定番
- **verbosity bias（長さバイアス）**：内容の質と関係なく、長い出力を「詳しくて良い」と判定しやすい傾向がある。評価基準に「簡潔さ」の観点を明示的に含めないと見落とされやすい

## 実務への接続

- チャットボットの応答トーン、要約の網羅性、RAGの回答が引用元と矛盾していないか、といった「正解が一つに定まらない」品質項目の継続監視に向く
- CI/CDのように、プロンプトやモデルを変更するたびに大量のテストケースを自動採点し、劣化（リグレッション）を検知する使い方が実務では中心になる
- 契約書チェックや医療情報の判定など、誤りの影響が大きい領域では、LLM判定はあくまで一次スクリーニングとし、最終判断は人が行う設計にする

## 講座で使うなら

- 30 秒説明: 「AIの答え合わせを、別のAIにやらせる方法です。ただし採点役のAIにも癖があるので、そこを疑う視点とセットで教えます」
- たとえ話: 生徒の作文を先生が1人で全部読むのは大変なので、別の採点係（LLM）に基準表を渡して先に振り分けてもらう。ただし採点係が「長い作文=良い作文」と勘違いしていないか、たまに見直す必要がある
- 演習案: 受講者が実際に使っているAIの出力を1つ選び、「Likert scale」「binary classification」のどちらで自動採点できそうかを議論させ、採点用プロンプトの基準文を実際に書かせる
